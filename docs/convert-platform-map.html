Crossovers

Overlaps and links worth designing for

Clients live in three places

Capacity client_keyClient hub repo slugPayload case studies

Make Capacity's client_key the only client ID. Add an optional clientKey to Payload case studies. Retire the client hub repo's model.

Partners live in three places

Payload partnersBrand Tools partners.jsonCapacity third parties

Payload becomes the partner list (it already joins to case studies). Brand Tools reads it for logos. Capacity links client usage to partner slugs.

Sidekick exports go nowhere

Sidecar Extension exportstrategy-session-prep skillClient hub strategy

The extension already exports Sidekick conversations to Markdown, which the strategy skill consumes. Later, attach exports to the client record in Capacity so they feed the client hub and workshops.

Claude skills run on manual exports

ux-auditconvert-client-hubworkshop-to-roadmapCapacity MCP

Skills take GA4, Jira, JPD and Tempo exports by hand. Capacity already has an MCP server with per-user tokens. Extending it gives skills live client context.

The static client hub skill overlaps the real one

convert-client-hub skillCapacity client hub

The skill builds static HTML hubs on Product UI. Once Capacity's hub is live, keep the skill for prospects and one-offs only.

Convert builds are already in Payload

Payload case studiesGreat Cartconvert-content skill

Case studies carry industry, features and partners, so Great Cart's "Convert" source needs no new data entry. The content skill already writes to Payload.

Inspiration feeds audits and pitches

Great Cartux-auditsales-to-discovery-prep

Audit recommendations and discovery prep can cite Great Cart examples by UX pattern. A board per client or pitch links them.

Hosting is spread across four platforms

VercelCloudflareGitHub PagesChrome Web Store

Payload already runs on Cloudflare (Workers, D1, R2) with a free tier that allows commercial use. That's the natural home when static apps need login.

Shared spine

2027, if Seb agrees

Decisions

What needs agreeing, and with whom

Is client_key the client ID everywhere?

Tom + Seb · P1

Cheap to agree now, expensive to fix later. No Capacity code changes needed.

Which system owns partners?

Tom · P1

Recommendation: Payload, because case studies already link to it.

GoodCart feed terms

Tom + GoodCart owner · P1

Format, refresh, image hosting, attribution, who builds team features.

Host and database for logged-in apps

Tom · P2

Cloudflare to match Payload, or Vercel to match Capacity. Supabase free tier for the database.

A Convert domain for the suite

Tom + Seb · P4

Subdomains of one domain are what make a shared login session possible.

Does Capacity become the identity provider and client API?

Seb · P4

The biggest dependency in the plan. Until agreed, every app keeps its own login.

Who owns the shared platform layer?

Tom + Seb + leadership · P4

Someone has to own the API, auth config and data contracts once more than one app depends on them.
